How to Use Cursor for Refactoring (A Repeatable Workflow)

Cursor’s agent is excellent at refactors that cross file boundaries and wasteful on the ones that do not. Here is the loop we run, the four prompts it runs on, and the numbers from running four real refactors twice.

The refactoring workflow that survives a real repository is four prompts long: commit first, state what must not change, make Cursor plan before it edits, then let the test suite referee the result. Cursor’s agent does the work that is genuinely tedious — renaming a domain concept across 34 files, splitting a 612-line component, collapsing three near-identical handlers into one — but only when you tell it where the boundary is. This is the loop, the rules file that carries your conventions, and the prompts we actually typed.

We ran four refactors twice in the same Cursor 3.7 Pro install: once with Agent mode and once with Tab and inline edit alone, no agent. The agent won all three refactors that crossed files — 5 files in 14 minutes against 47 minutes and three manual fixes for the component split, 34 of 34 renamed files against 31 of 34. It lost the contained one outright: a 40-line local rename took three minutes by hand and produced a 9-line diff against the agent’s 11. Knowing which of the two you are doing is most of the skill.

Bottom line: Use Agent mode for anything that touches more than two files, and put your conventions in a .cursor/rules/ file so you stop repeating them. Commit before you start and check the suite after every step — checkpoints roll back Cursor’s edits, not Git history. Do the small, contained rewrites by hand with Tab and Cmd+K; it is faster and the diff is cleaner.

Step 0: Make the Refactor Reversible Before You Type Anything

Two things go wrong with AI refactors, and both are bookkeeping: a diff so large that review becomes rubber-stamping, and a suite that was already red before the agent started, which makes every later failure ambiguous. So get the tests green, commit, and work on a branch you are willing to delete. Cursor checkpoints are stored locally and separately from Git — they restore files in a session, but they are no substitute for a commit you can diff against later.

The Prompt Has Four Parts

Every refactor prompt we write has the same shape, and the two parts people skip are the ones that cause the rework.

1. The goal, with the file named

Use @ mentions rather than describing files from memory: @src/billing/InvoiceConsole.tsx for a file, @src/api/invoices/ for a folder, @Codebase when you want it to search for a symbol everywhere. The index exists; use it before the model has to guess.

2. The invariant — what must not change

This is the sentence that separates a refactor from a rewrite. “The public props must not change, the table DOM must not change, and you may not edit anything under __tests__/.” In our component split the agent changed one prop type anyway, and because the invariant was written down, we caught it in review instead of in production.

3. The boundary — what is out of scope

Name the things a helpful model will otherwise decide to improve: route paths, log message text, error codes, dependency versions, formatting of files you did not ask about. Scope creep in a refactor is the same as a behaviour change with worse review.

4. The proof — how you will both know it worked

“Run npm test -- invoices and report the result” or “the 17 tests in invoices.test.ts are the contract; if they need changing, stop and ask.” An agent that is allowed to edit the tests has no referee at all.

Put the Conventions in a Rules File, Not in Every Prompt

Rules are instructions Cursor loads into context automatically, which is why they are the highest-leverage configuration in the tool: you write the constraint once instead of in every prompt. Project rules live in .cursor/rules/ as .mdc files with frontmatter — a plain .md in that folder is ignored — and AGENTS.md in the project root is the one-file alternative. The frontmatter decides when a rule loads: alwaysApply: true for standards, a globs pattern for one corner of the codebase, or a description the agent matches on its own. Team rules outrank project rules, which outrank user rules.

Our refactoring rules file is short, and every line in it exists because the agent got something wrong at least once:

Refactors must be behaviour-preserving. Never edit files under __tests__ or *.spec.*. Keep barrel exports in sync when files move. One logical refactor per commit. Run the nearest test file after every edit and report the result. Do not add dependencies. When a public signature has to change, stop and ask.

The Four-Prompt Loop

Inside Agent mode, Shift+Tab rotates between Agent, Ask and Plan. Refactoring should start in Plan: it researches the codebase, asks questions if it needs to, and writes an implementation plan you can edit before anything touches disk. Cursor’s own advice when a build drifts is to revert, sharpen the plan and re-run rather than patching an off-track agent with follow-ups, and that is the rule we follow.

The four prompts, in order: plan it, correct the plan, apply and prove, then audit your own diff. The fourth is the one people skip and the most useful: asking the agent to name the behaviour it cannot prove unchanged turns it into a reviewer of its own work, and it usually points at the untested path you were worried about. Then read the diff hunk by hunk and keep one refactor per commit so the next one starts from a clean base.

What It Cost, and Which Model

On Cursor’s published rates the model you pick changes the bill more than the size of the refactor. All four of our refactors on Composer 2.5 metered out at $1.74 and drew from Cursor’s own first-party pool; the identical four pinned to a frontier Claude model cost $11.20 from the third-party pool, because that pool is billed at Anthropic’s API price. Composer 2.5 costs $0.50 per million input tokens against $4 for the frontier model we tested, and for mechanical work — moves, renames, extractions — we could not tell the results apart. Reserve it for the refactor where two similar implementations have to be reconciled without changing either one’s behaviour.

Where the Agent Loses

Three situations where doing it yourself is the better call. Contained edits: four renames inside one function is an inline edit, not a planning exercise. Untested behaviour: no agent can prove it preserved something no test covers, so write the test first or accept that you are reviewing by eye. Refactors that are really redesigns: if the invariant is “make this better”, you are paying for an architecture you will review anyway. And when a refactor has to land as one reviewable change, an agent that edits 34 files at once produces a diff nobody reads carefully — split it by design, or use a PR-centric flow instead.

Frequently Asked Questions

Can Cursor refactor across multiple files safely?

Yes, and that is the case it is genuinely good at, provided the tests exist. In our run it renamed a domain concept through all 34 files that referenced it, including fixtures and API mocks, while a grep-assisted manual pass found only 31 and missed three behind a dynamic reference. The safety comes from the referee, not the agent: name the test file in the prompt as the contract and forbid edits to it.

Should I use Agent mode or inline edit for refactoring?

Agent mode for anything crossing a file boundary or changing a shared type; Tab and Cmd+K inline edit for anything inside one function. The agent took 14 minutes and produced five correct files for a component split that took 47 minutes by hand with three fixes afterwards, but a contained 40-line rename took three minutes by hand with the smaller diff. If you can describe the change in one sentence without naming a second file, do it inline.

Do I need to commit before asking Cursor to refactor?

Always. Cursor creates checkpoints automatically before significant changes and you can restore any of them from the chat timeline, but checkpoints are local and separate from Git — they restore files, not history, and they cannot tell you what the code looked like before the session began. A commit gives you the diff you actually need for review, and it makes the one-logical-refactor-per-commit discipline possible.

Which model should I use for a refactor in Cursor?

Cursor’s own Composer 2.5 for mechanical work, a frontier model for the refactors where the reasoning is the hard part. Composer 2.5 costs $0.50 per million input tokens against $4 for the frontier Claude model we tested, and on renames, file splits and extractions the two produced equivalent diffs. That choice also decides whether the work draws from the generous first-party pool or the metered third-party one.

Final Verdict

Cursor’s agent is the right tool for the refactors that are boring because they are wide, and Tab with inline edit is the right tool for the ones that are boring because they are small. Across four refactors run twice in the same install, the agent took 3 of 4 — 34 of 34 files renamed where a manual pass reached 31, a 612-line component split into 5 files in 14 minutes with the suite green, and three duplicated handlers collapsed into one with the response shape intact. It lost the contained rename, and that is not a flaw in the tool.

What actually decides the outcome is not the model you pick, it is whether you wrote down what must not change and named the test that proves it. Do that in a rules file and it is one line per refactor; skip it and you will be reviewing a diff you cannot verify, at a price you did not budget for.

12 to 15 October 2026 — four real refactors on one 11,400-line TypeScript and React billing console with 254 Jest tests and 61 Playwright tests, all green at the start. The same four prompts were used both times, with the agent-specific instruction to run the tests removed for the manual pass.
